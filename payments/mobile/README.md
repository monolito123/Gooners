# goonersPAY merchant apps

The merchant app for Android and iOS: a phone becomes a payment terminal (card and Pix), shows what the store has to receive, sends payouts by Pix, and the owner's phone manages which phones may sell. The design is in [docs/05](../docs/05-mobile.md); this folder is the first working version.

| | |
|---|---|
| [`conformance/vectors.json`](conformance/vectors.json) | Test vectors generated by the platform (`cd ../platform && go run ./cmd/conformance`). Both cores and the spec checker reproduce them byte for byte. CI fails if they are stale |
| [`android/core`](android/core) | Kotlin core (JVM library): money, NIP-01 events and BIP-340, NIP-19, NIP-98 login, DPoP proofs, the kind 17710 device list, BR Code checks, the sandbox card format, the checkout state machine and the API client |
| [`android/app`](android/app) | Jetpack Compose app (Android 11+) |
| [`ios`](ios) | `GoonersPayKit`, the same core as a Swift package (CryptoKit, swift-secp256k1); it builds and tests on Linux and macOS |
| [`ios/App`](ios/App) | SwiftUI app (iOS 17+), generated as an Xcode project by XcodeGen |

## What the apps do

1. **Pairing.** A partner (or the owner's app) creates a single-use enrollment code for a merchant (`POST /v1/merchants/{id}/enrollment-codes`). The phone reads it with `GET /v1/enrollment`, generates its keys and enrolls with `POST /v1/enrollment`. On the merchant's first phone it also creates the **merchant root key** and shows it once for the owner to write down (docs/03 §4.1). A phone never holds an API key.
2. **Login.** Every 15 minutes the phone signs a NIP-98 event (kind 27235) over the exact login request with its **device key**. The session it gets is bound to a **DPoP key** (RFC 9449) that never leaves secure hardware, and works only on the merchant-app routes, for this merchant and this phone's terminal (docs/02 §3.2).
3. **Selling.** The keypad, then a card through the reader and `POST /v1/terminal/authorizations`, or a dynamic Pix QR polled until it is paid. The app checks the BR Code's CRC and amount before the customer sees it. An approved sale shows the receipt QR the customer scans to claim it.
4. **Money.** Balance, pending receivables by date, recent entries, and a Pix payout: a quote first (fee and net shown), then a fresh biometric confirmation, then the payout.
5. **Devices (owner).** The owner's phone adds a cashier phone by its `npub`: the root key signs a newer device list (kind 17710) naming both. Removing a phone signs a list without it, which ends its sessions and revokes its terminal at once.

## Keys on the phone

| Key | Android | iOS | Used for |
|-----|---------|-----|----------|
| DPoP (P-256) | Keystore, StrongBox when present; never exportable | Secure Enclave (CryptoKit) | Every request's proof |
| Device (secp256k1) | Random, wrapped by a Keystore AES-256-GCM key that needs biometrics or the device credential (30 s window) and is invalidated by a new fingerprint | Random, ECIES-encrypted to a Secure Enclave key that needs Face ID (`biometryCurrentSet`) or the passcode | Signing logins; unwrapped only for the signature and wiped after |
| Merchant root (secp256k1) | Same as the device key, owner's phone only | Same | Signing device lists |

Both apps refuse to pair a phone without a screen lock in release builds, keep secrets out of backups, block screenshots (Android) or hide the screen in the app switcher (iOS), and refuse redirects so a session token never follows a 3xx elsewhere. Release builds speak HTTPS only.

Card reading is behind one interface (`CardReader`). Production plugs in the licensed MPoC SDK on Android and ProximityReader (Tap to Pay on iPhone) or a PCI PTS reader on iOS; they encrypt inside their secure boundary and the app only forwards the blob. Until those contracts exist, the only reader is the **sandbox reader**: it "taps" scheme test cards in the development format the sandbox decrypts, which the platform refuses in production.

## Run it against the sandbox

```bash
# 1. The sandbox: platform, card scheme and Pix PSP simulators, on a fresh database.
cd payments/platform
DATABASE_URL=postgres://… go run ./cmd/smoke -serve /tmp/sandbox.json
# /tmp/sandbox.json now holds api_url, a partner api_key, dev_card_key and a merchant.

# 2. Tests of both cores, including the whole protocol against that sandbox.
cd ../mobile/android && GOONERSPAY_SANDBOX=/tmp/sandbox.json ./gradlew :core:test
cd ../ios && GOONERSPAY_SANDBOX=/tmp/sandbox.json swift test
```

The integration tests create a merchant and an enrollment code with the partner key, then enroll a phone, log in, sell by card and by Pix, pay out, add a cashier phone and remove it. Without `GOONERSPAY_SANDBOX` they are skipped and the conformance tests still run.

**Android app.** JDK 21 and the Android SDK (platform 37). `./gradlew :app:assembleDebug` builds `app/build/outputs/apk/debug/app-debug.apk`. On an emulator the default platform address is `http://10.0.2.2:8080` (the host machine); debug builds allow cleartext to it. Create an enrollment code (`POST /v1/merchants/{id}/enrollment-codes` with the partner key), type it in the app, and paste the sandbox's `dev_card_key` to enable the sandbox reader.

**iOS app.** Xcode 16.3 or later and [XcodeGen](https://github.com/yonaskolb/XcodeGen) 2.46: `cd ios/App && xcodegen generate && open GoonersPay.xcodeproj`. The simulator has no Secure Enclave, so there the keys are kept in the keychain unwrapped (development only); run on a device to use the Enclave and Face ID.

## Status and next steps

Built and tested: pairing, the root key backup, NIP-98 login with DPoP sessions, card sales through the sandbox reader, Pix, receivables, payouts with biometric step-up, and device management, on both platforms. CI (`.github/workflows/payments-mobile.yml`) runs the conformance and sandbox tests of both cores, builds the Android app (debug, minified release, lint) and the iOS app for the simulator and for devices.

Not built yet, in the order they matter:

1. **Real card acceptance**: the MPoC SDK adapter (Android) and ProximityReader (iOS), which need the vendor contract and Apple's Tap to Pay entitlement.
2. **Attestation verified by the platform**: the apps send App Attest evidence (iOS) and have the seam for Play Integrity (Android), but the sandbox's attestor only records it. Phones added by the owner (rather than with an enrollment code) send no evidence; production must attest them at their first login.
3. **Certificate pinning** for the platform's API host, and the mTLS terminal certificate of docs/05 §2.4.
4. **The offline outbox and the terminal journal** (docs/05 §2.5): sales today need the network.
5. **Reading the cashier's `npub` by camera** on the owner's phone (it is typed or pasted today), localization beyond pt-BR, and the sunlight theme.
